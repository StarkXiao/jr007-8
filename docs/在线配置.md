# 在线配置：分类、属性表单与业务阈值

分类、动态属性表单（属性 Schema）与业务阈值不再写死在代码里，统一在管理后台
**「在线配置」**（`/admin/config`）维护，支持**草稿预演 → 灰度生效 → 全量发布 → 一键回滚**。

## 1. 数据模型

一张 `app_config_versions` 表，每一行是一份**完整配置**（所有分类 + 所有阈值），状态四选一：

| 状态 | 含义 | 数量约束 |
| --- | --- | --- |
| `draft` | 草稿，可反复改，对线上零影响 | 至多一个 |
| `canary` | 灰度中，只有命中规则的用户读到 | 至多一个 |
| `active` | 当前全量版本 | 恰好一个（出厂引导保证） |
| `archived` | 历史档案，永不删除 | 不限 |

版本号只增不减。**发布不是改指针，而是 append 新版本**；回滚也是「把历史内容重新发一个新版本」，
审计链永远不断。

配置内容（`payload`）：

```jsonc
{
  "categories": [
    {
      "code": "bench", "name": "长椅", "icon": "bench", "color": "#8B5E3C",
      "description": null, "sortOrder": 1, "isActive": true,
      "schema": { "type": "object", "required": ["condition"], "properties": { /* … */ } }
    }
  ],
  "thresholds": {
    "staleReportThreshold": 3,
    "commentEditWindowMinutes": 10,
    "reviewLockMinutes": 30
    // …完整清单见后端 THRESHOLD_SPECS
  }
}
```

阈值注册表（键、标签、单位、取值范围、默认值）唯一来源：
`backend/src/modules/config/types.ts` 的 `THRESHOLD_SPECS`，前端编辑表单与后端校验都从它生成。

## 2. 生命周期与 API

所有接口仅管理员（`admin`）可用，均写审计日志（`config.*` 动作）。

| 动作 | 接口 |
| --- | --- |
| 阈值注册表 | `GET /admin/config/threshold-specs` |
| 版本档案 + 当前三个指针 | `GET /admin/config/versions` |
| 取/建草稿（基于当前生效内容） | `POST /admin/config/draft` |
| 保存草稿（不触碰线上） | `PUT /admin/config/draft` |
| 丢弃草稿 | `DELETE /admin/config/draft` |
| **草稿预演**（模拟某用户命中哪版） | `POST /admin/config/preview` |
| 灰度发布 | `POST /admin/config/publish-canary` |
| 灰度扩/缩量（不产生新版本） | `PUT /admin/config/canary/rollout` |
| 灰度撤回为草稿 | `POST /admin/config/canary/revoke` |
| 灰度转全量 / 草稿全量发布 | `POST /admin/config/publish-full` |
| **一键回滚到任意历史版本** | `POST /admin/config/rollback/:version` |

## 3. 灰度规则（`rollout`）

多条件之间是「或」，任一满足即命中；游客永远不命中灰度：

```jsonc
{
  "percent": 20,              // 按用户 UUID 的稳定哈希取 0–99 桶，同一用户每次结果一致
  "roles": ["admin"],         // 命中角色
  "userUuids": ["…"],         // UUID 白名单
  "userModBase": 10,          // 用户数字 ID 对 10 取模
  "userModRemainders": [0, 1] // 余数为 0 或 1 的用户
}
```

稳定桶用 FNV-1a 派生（`validate.ts` 的 `stableBucket`），保证灰度名单不随刷新乱跳。

**预演**：在配置中心输入任意用户的 ID/UUID/角色，后端返回 `matched` 与中文原因
（命中了哪条规则 / 桶号是多少），不写任何数据。

## 4. 读取语义（关键设计）

- **用户请求**按当前登录用户解析：命中灰度 → `canary`，否则 → `active`。
  入口 `resolveConfig(user)`，单个阈值用 `getThreshold(key, user)`。
- **系统/定时任务**（worker）只读 active：`resolveSystemConfig()`——灰度规则绝不影响批处理。
- **条目的校验一律按「条目标作者」命中的版本**，而不是操作者：
  提交审核、自动预检、审核通过、申诉改判都解析作者的配置。
  否则灰度用户按新表单填的内容，会被审核员视角的旧 Schema 卡掉。
- 评论编辑窗口、审核锁、举报合并窗口、签名 URL TTL 这类**行为阈值**，按「行为发起者」命中的版本取值。
- 解析结果在每个进程内缓存 30 秒；任何进程发布/回滚后通过 Redis pub/sub
  （`psdm:config:invalidate`）主动通知所有 API/worker 立即失效。Redis 不可用时退化为 TTL 兜底。

## 5. 分类物化：为什么还要保留 `categories` 表

`spots.categoryId` 是数据库外键，分类不能只存在 JSON 里。发布时把配置物化回 `categories` /
`category_schemas` 表：

- **全量发布**：增删改全部对齐；从配置里移除的分类置 `isActive=false`（历史条目外键不断，新提交不可再选）。
- **灰度发布**：新增分类以 `isActive=false` 补建行（供外键使用），**绝不修改任何现有行**——
  保证未命中灰度的用户看到的世界完全不变；同时写一份非 current 的 canary schema 备查。
- **回滚**：等同一次全量发布，物化结果与目标版本完全对齐。

## 6. 新增一个可配置阈值要改哪里

1. `backend/src/modules/config/types.ts` 的 `THRESHOLD_SPECS` 加一项（key/标签/单位/范围/默认值）。
2. 业务代码把原来的常量引用换成 `await getThreshold("yourKey", user)`。
3. 不用写迁移、不用改前端——配置中心的编辑表单由注册表自动生成。

出厂默认分类与阈值在 `backend/src/modules/config/defaults.ts`；全新部署启动时
`ensureBootstrapConfig()` 用它写入 v1（带 advisory lock，多进程同时启动也只写一份）。

## 7. 前端

- 配置中心：`frontend/src/pages/ConfigCenterPage.vue`（阈值表单、分类/属性编辑、灰度规则、预演、版本回滚）。
- 分类编辑：`frontend/src/components/CategoryConfigEditor.vue`（字段级可视化编辑，不再需要手写 JSON）。
- store：`frontend/src/stores/config.ts`；`/categories` 响应带 `configStatus`，
  命中灰度的用户其分类数据标记为 `canary`。
